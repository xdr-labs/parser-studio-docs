## Walkthrough

1. Paste the **complete 16-line issue report stack trace**, into **Auto Parser → Add Logs**.
2. Click **Analyze Logs**. Look at the number of logical events reported. This official GitHub issue contains a single Java exception spread over 16 physical lines. Default analysis showed **0 of 16 lines completely parsed**; this is not a successful generated parser.
3. If the app offers **These look like Java error stack traces**, read the explanation and use **I Confirm Each Java Error Is Separated by a Blank Line** only when it matches the actual way records are separated at the source.
4. The real **0 of 16** result does not qualify the source for parser creation. First establish actual event boundaries.
5. Retain all original bytes; only create a native parser after a separately validated multiline rule passes the complete test.

## Expected review outcome

The source exception is one logical event but the current public UI reported **0/16 complete physical records** with default settings. Confirm the true event boundary before applying a multiline rule; do not claim a verified parser from this unreviewed source.

## Recovery path

If your source does not reliably separate complete exceptions by blank lines, **do not** select that confirmation just to force generation. Obtain the actual message boundary from the log source first.

<Note>
  You do not need to know the term "multiline framing" before pasting. You only need to confirm how **one complete error ends** when Parser Studio asks.
</Note>
