# Review and correct normalized mappings

**Goal:** Keep source extraction intact while assigning accurate, consistent output field names.

## Fictional sample

~~~json
{"action":"blocked","client_ip":"192.0.2.44","server_ip":"198.51.100.8","server_port":"443","device_build":"9.1-demo"}
{"action":"allowed","client_ip":"192.0.2.45","server_ip":"198.51.100.9","server_port":"80","device_build":"9.1-demo"}
~~~

## Walkthrough

1. Paste the two events in **Auto Parser**, analyze and continue to **Review Fields**.
2. Confirm the source values for action, client_ip, server_ip, server_port and device_build.
3. Select **Map Fields**. Search for appropriate destinations in the Stellar field catalog.
4. Treat the labels “client” and “server” as source semantics until the target catalog provides an exact compatible definition; do not equate them automatically with source/destination roles.
5. If a network-port destination is supported, select the port value type and confirm that numeric text is handled according to the displayed rules.
6. Keep device_build in the vendor/custom group if no supported catalog field exists.
7. Correct any collision or unsupported target and re-run the complete sample test.

## Expected review outcome

Every source value has at most one intended meaning, destinations do not conflict, and each chosen type is compatible with all tested values.

## Recovery path

If a catalog field is marked as system-managed, unverified or type-incompatible, choose another supported mapping or retain the original field in the vendor group. Never hide a blocking finding by renaming a value to an unrelated destination.
