# Training case 05 — synthetic RFC3164 relay wrapper

Product behavior anchored to [Parser Studio main a4b4e2f](https://github.com/xdr-labs/parser-studio/commit/a4b4e2fba54588fa2b9807e1cfeed49190061927).

These are **synthetic instructional records**, not copied from a customer or claimed as official Fortinet output. They use FortiGate-like key/value field names and reserved documentation IP ranges (RFC 5737).
- 05-relay-original.log: the two unmodified application event bodies, before forwarding.
- 05-relay-forwarded.log: the same two bodies with an RFC3164-formatted header generated by the simulated relay `relay01`; the header contains PRI, variable timestamps and `forwarder:` application label.
- 05-relay-holdout.log: a different test message, not used to build a rule.

This exercise proves only what its validation observes. In Parser Studio choose **Optional: declare Syslog forwarder hostnames**, enter `relay01`, set maximum hops `1`, check `2 of 2` in relay preview and **Apply declared relay profile**. Then analyze. Wrapper bytes must remain preserved in original source.

It does **not** verify TCP/UDP receipt or any Stellar Cyber production ingest. The browser UI takes pasted/uploaded records, not a live syslog feed.

The optional `replay_relay_loopback.py` exercise performs two real UDP hops on loopback and verifies its captured output is byte-for-byte identical to the published forwarded fixture. No external network target is contacted.
